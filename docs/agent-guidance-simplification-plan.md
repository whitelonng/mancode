# 模型与项目约束的平衡：修改方案

状态：生成器、契约、获批恢复补修和当前项目 Codex 入口升级已完成。新增三类 Codex 分支、六个样例实测已收尾；四例独立发现的缺陷已另行补修并通过复测，首次结果保留，详见第 10 节。其他宿主与模板优劣对照不扩大结论。更新：2026-09-13。

## 一屏版

**目标：man 保持强工程治理；普通 Solo 保持轻量。** man 面向长任务和项目交付，优先保证代码质量、可接续性与工程标准，可以承担必要的记录、验证和审核成本。模型在已确认的工程边界内选择实现方法。

| 模式 | 保证什么 | 留给模型什么 |
|---|---|---|
| 显式 man | 需求与决策持久化、确认计划、范围控制、阶段接续、真实验收、审核修复闭环 | 范围内的调查路径、算法与工具选择、具体实现；不自行省略治理阶段 |
| 普通 Solo | 授权范围、相称验证、真实报告、必要的 diff 自检 | 自行安排执行，不强制建任务、正式计划、发现编号或独立 reviewer |
| man → Solo handoff | 原需求、已确认计划、文件范围、必需验收与 handoff 完成协议 | 仅简化受支持的执行方式；不因进入 Solo 而丢弃原任务承诺 |

本次调整的主轴是分清模式职责。不会要求 man 与 Solo 一样短，也不以少记录、少测试、少审核衡量 man 的成功。

| 顺序 | 要做什么 | 做完后的变化 |
|---|---|---|
| 1 | 先明确 man、普通 Solo 与 handoff 的不同标准 | man 治理完整，普通 Solo 不承担整套流程 |
| 2 | 精简常驻说明 | 普通任务不用读取整套模块交付细节 |
| 3 | 整理 Skill 并修正作用域歧义 | man 保留工程闭环，模型在授权边界内自主执行 |
| 4 | 更新测试与项目文档 | 验证实际边界，避免把每句旧措辞永久锁死 |
| 5 | 分模式做隔离对照 | man 通过长任务与接续验证；普通 Solo 减少无必要操作 |
| 6 | 通过现有升级流程更新入口 | 用户内容、历史任务与原有保护继续有效 |

保留三条底线：不擅自扩大范围；不伪造验证；未达到验收不能声称完成。

## 0. man 的工程质量要求

以下均依托已有 plan、requirements、review/verification ledger、Context Pack 和 checkpoint 能力，不新建第二套状态。

| 环节 | 必须保留的要求 |
|---|---|
| 调研 | 核对项目事实、相关架构、调用链、兼容影响与风险；重大事实有证据，假设明确标记 |
| 需求 | 已确认范围、技术决定、默认值、排除项和必需验收持久化；等待回答前保存已知决定和 blockingUnknowns，不能只留在聊天里 |
| 计划 | 清楚定义可验收结果、实施阶段、依赖与相关集成验证；按当前 policy 完成计划与 implementationScope 确认 |
| 执行 | 改动追溯到已确认目标；遵守现有架构和文件边界，保持可诊断错误处理，避免无依据抽象和扩张 |
| 阶段接续 | 在实质阶段结束、需要等待或交接时，使用既有记录保存实际进度、剩余事项和证据；不为每个工具调用新增记录 |
| 验证 | 运行项目要求的检查；覆盖已确认用户行为、受影响调用链、必要负向/权限/兼容路径与集成结果；局部单测不能替代项目级验收 |
| 审核 | 审查批准目标与完整模块 diff、入口调用链、正确性、风险和复杂度；有条件且获授权时优先独立审核；自审不能冒称独立，明确要求独立审核时不得自行降级 |
| 修复闭环 | 具体 finding 保留稳定 ID，修复后复验并登记解决情况；不删除 finding 来放行，不因“只审一次”忽略新回归 |
| 完成 | 必需行为、有效证据、所需审核与记录均达标，并通过原完成门禁；所有局部任务通过不自动等于整个项目验收通过 |

这些要求属于 man 的交付承诺。模型可以选择怎样做好每一环，但不能为了提速改用普通 Solo 标准。已有 plan_only 决定仍止于规划；进入 governed_execution 后，在已确认范围内继续执行，不在每个阶段重复请示。

恢复长任务时先读取原 TaskRef 和对应 Context Pack、该任务模式入口、批准计划及当前记录，再继续缺失部分。不能只读任务摘要和轻量 bootstrap 就执行 man。会话变化本身不废弃证据；源码、依赖或相关环境变化必须重新核对适用性。不能因为流程复杂、上下文变长或工具暂时不可用而静默切换模式或降低验收。

## 2. 第一项：明确授权与暂停条件

授权解释在 bootstrap 和相关模式入口中保持一致；流程强度明确按模式区分。不能用共用的“轻量执行”句子覆盖 man 的需求、计划、接续和质量环节。

| 现在的问题 | 改成什么 |
|---|---|
| “所有 mutation 必须通过 CLI”可能包含正常代码修改 | 仅 Continuity 的权威状态通过公共 CLI 修改；代码和文档依照任务授权修改 |
| 没有 TaskRef 时要求停止，可能误伤普通讨论 | 停止无授权的治理操作；普通问题和 Solo 任务继续处理 |
| 涉及 API、并发等领域就可能再次请示 | 先判断具体影响和既有授权；主题名称本身不触发重复确认 |
| 项目可查明的问题仍可能要求用户决定 | 先查仓库；仅将无法自行确定且会改变结果的决定交给用户 |

拟采用的核心措辞：

> 已有授权覆盖当前动作且事实前提未变时继续执行。发现真实冲突、超出授权的新影响，或会改变行为、范围、验收、数据、安全和兼容性的未决决定时，暂停受影响动作并提出聚焦问题。独立且已授权的工作可以继续。项目明确要求的审批仍须遵守。

“不重复请示”不等于自动批准新迁移、删除、发布或权限变化。风险仍决定验证深度。显式治理任务继续使用已有 plan confirm、scope change、reframe 等协议；不因提示变短而绕过这些操作。

普通 Solo 不因跨文件数量就自动进入治理；出现真实的架构、迁移、语义所有权或跨模块验收决定时，沿既有规则推荐 man，不自行升级权威。自然语言研究/计划请求与显式模式入口沿用既有授权语义。已经显式进入 man 的执行任务不因“模型能自己做”而省略治理，也不得静默切成 Solo。man → Solo 只通过用户选择和既有 handoff 协议执行；继承计划与验收，不适用普通无任务 Solo 的豁免。

## 3. 第二项：精简 AGENTS.md / CLAUDE.md 的常驻内容

常驻保留：项目命令与必要约定、man 强治理与普通 Solo 轻量的区别、handoff 继承约束、授权与真实证据边界、可信状态入口、选择固定 CLI 的规则，以及找到模式入口的方法。明确声明：普通 Solo 的轻量条款不适用于活动中的 man、manteam 或有明确承诺的 handoff。

bootstrap 明确导航：存在当前或用户指定 TaskRef 时，依据真实任务的模式读取对应现有入口和其 policy 规则；用户无需在每个新会话再次输入 /man。没有任务时才使用普通 Solo 的默认入口。新建、恢复、plan_only 后明确恢复、旧 policy 和显式 handoff 都必须覆盖，不能把所有恢复任务默认当成新 delivery task。

对 session、TaskRef、revision 保留必要导航；详细操作放在实际进入模式的段落。各模式应能够独立被调用；新会话仅加载该模式入口时仍能恢复正确流程。不能为消除跨文件重复而删掉启动、接续与恢复所需信息。

将以下**已明确只适用于新 man 模块交付**的内容，从常驻块归入已有 man.actions 并合并重复表述：

- 计划文件和交付区的规则。
- 相关架构资料的读取与缺失处理。
- 项目进度页的 JSON 契约与同步方式。
- 模块提交、发布事实及工程执行提示。

移动前逐项对应原规则与新位置，确认内容完整且在相关 man 阶段可读取，不把“移出常驻”做成“删除 man 约束”。保留它们原有的 policy 3 适用条件，不能使旧任务或其他模式开始执行新流程。特别保留未读到架构时不编造、进度页缺契约不阻塞开发、未发布不冒称已发布等语义。

UI 规则本轮保留现有偏好及例外：遵循设计系统、不用 emoji 作为界面图标、已有方向和局部修复无需重新选方向。不会在未有可用按需入口时直接删除这些要求。

不按固定行数或 token 上限验收；减少无关任务的负担才是目的。

## 4. 第三项：man 保持完整流程，Solo 放开步骤

| 内容 | 修改方式 |
|---|---|
| 调研前提、事实与推断 | man 与 manteam 保留有证据的结构化发现与处置；允许零发现。普通 Solo 不运行整套 Scout 流程 |
| 发现编号与分类 | 本轮保留 man / manteam 的既有 F-ID、分类和处置规则，不以节省文字为由删除。实际 reviewer finding ID 更不能删；表达精简仅影响无协议要求的说明 |
| 建议、已确认行为、技术决定、排除项 | 保留语义区别；不能把未接受建议写成已授权需求 |
| 已明确需求的重复澄清、伪造多个方案 | 复用确认过的决定，不制造伪选项；man 仍要完成需求就绪检查、实际决策记录与计划确认 |
| 领域知识、必要工具用法、输入格式 | 保留必要信息；合并重复说明，不让模型猜私有协议 |
| 记录与审核 | man 的批准计划、实质阶段进度、验证与审核记录为必需交付；只合并等价副本。普通 Solo 不强制另建正式计划或独立 reviewer，但仍需相称验证与 diff 自检 |
| 复核与重测 | 围绕真实改动、新证据和直接回归执行；复用仍适用证据 |
| 可选 Skill 缺失 | 已有授权、资料和等价方法足够时继续；不得绕过用户指定工具或降低验收 |

一次模块总审继续作为新 delivery 任务的默认流程；出现具体修复或新风险时允许必要补查，避免将“一次”误读成禁止进一步检查。保留必需审核与现有 skip/waiver 的授权条件，不改变其他 policy 的轮次和状态机。

针对某模型的重复读取、哈希等效率提示，归并到原本适用的模式。保留原有工程准则和必要完整性检查的例外，不在这轮修改中顺带将 man 工程要求整体降为建议。若无新证据支持删除则先保留，效率提示不得压过完整 diff 审核、真实验证、跨阶段读回或证据适用性检查。

**本轮不新增 references 文件。** 当前安装、摘要和恢复只识别固定文件集合。JSON 示例和罕见恢复配方先在原模式内按用途分组、压缩重复；没有可发现的替代说明时保留原配方。未来若确需拆文件，应单独补齐安装和恢复支持，不能链接到用户安装中不存在的源码 docs。

## 5. 验收：什么叫改好了

| 编号 | 必须观察到的结果 |
|---|---|
| AC-1 | 普通解释和无治理任务的 Solo 不因缺少 TaskRef 创建状态或中止；显式 man 与 man→Solo handoff 必须使用已有权威和协议 |
| AC-2 | 已授权且前提未变的 API/并发修复继续执行；真实冲突或新增未授权影响仍提出必要问题 |
| AC-3 | man 完成有依据的调研、需求/决定记录、计划确认、阶段接续、验证与审核闭环；普通 Solo 不承担这些正式流程 |
| AC-4 | 授权范围、scope/revision/plan 门槛、任务 policy 及团队 ownership 继续有效 |
| AC-5 | 真实验收不足时保持未完成；不以 exit 0、surface 标签或自述代替行为证据 |
| AC-6 | 可选 Skill 缺失不自动废弃有效证据；代码或相关环境变化时重新核验适用性 |
| AC-7 | 八个平台生成入口均符合契约，用户自写内容保留；共享入口、旧任务和其他模式没有语义误改 |
| AC-8 | man 以长任务质量、项目集成结果和跨会话一致性验收；Solo 单独衡量不必要操作是否减少，两类结果不混成平均分 |
| AC-9 | 会话中断、未决需求、修复、依赖/环境变化后仍能读取原任务并继续；不丢决定、不伪造新授权、不静默降级为 Solo |
| AC-10 | 局部验证通过但跨层用户流程失败时不能交付；修复后按原证据失效契约补齐验收，不能仅关闭 finding 或重写总结 |

man 的必要验证、审核和记录增加耗时不算失败；与其减少 token，更优先保证工程结果。没有测到 Solo 效率改善时如实说明。错误完成、越权、伪造证据、漏验收不能由速度或 token 节省抵消。

### 真实宿主对照

固定基线包与精简候选包：两者的业务和治理运行时代码一致，差异限于本方案的模板内容及相应契约。各组用自己的固定 CLI 初始化独立项目，组内不混用二进制。普通任务加载对应 bootstrap；显式模式任务加载对应 bootstrap 和模式入口。两组保持用户提示、业务代码、授权、工具、领域资料和测试一致，只改变被研究的指令。

必须让候选入口与对应 renderer 的摘要检查一致；不得直接覆盖 Skill 后制造 stale，再把治理失败算成模型问题，也不得关闭摘要检查来运行试验。

先跑已有短场景检查明显回退，然后必须增加 man 长任务场景。短 CSV 成功不能作为本方案完成验收。

| 场景 | 必须核对 |
|---|---|
| 普通 Solo 解释与小修复 | 不建治理状态，不重复询问已批准内容，相关验证和 diff 自检确实执行 |
| man 需求未决时跨会话接续 | 首个真实会话保存已知需求、决定与未决问题；新会话读回并处理既定用户答案，不重新问已回答问题、不假定确认 |
| man 跨 API、业务与存储层的分阶段交付 | 批准计划包含相关架构、阶段与集成验收；在阶段边界换真实会话，保留原任务和已完成工作，完成原授权范围内的剩余部分 |
| 局部通过但集成失败 | 独立 oracle 验证真实用户路径或权限边界；模型不得以各层单测成功宣称完成 |
| 审核发现实际缺陷后接续修复 | 发现有稳定 ID 与因果证据；新会话修复、补受影响验证、正确登记解决情况，不能删掉记录或漏做失效验收 |
| 真实需求变化或新高风险影响 | 只暂停受影响的未授权动作；按原协议对齐需求，已获批准的部分不重复确认 |
| HTTP 能力缺失 / 可选 Skill 缺失 / 内容或环境变化 | 分别保持未验证、复用有效证据、重验真正失效证据；不得静默降低标准 |
| man → Solo handoff | 普通 Solo 的豁免不覆盖原需求、计划、scope、必需验收和 handoff 完成条件 |

其中至少一个 man 放行案例必须连续完成同一目标的完整路径：未决需求澄清 → 保存并换真实会话恢复 → 计划确认 → 跨层分阶段实现 → 集成失败被识别 → 登记并修复原 finding → 复验与审核入账 → 原完成门禁通过。该连贯案例至少跨两个真实宿主会话；不能将多个脚本初始化的小测试拼成“长任务成功”。另覆盖 plan_only 只规划而不实施、明确恢复后的执行，以及真实新事实触发 realignment。

失败与恢复分支使用两组一致的可复现故障或外部变化，不要求模型故意写错代码，也不因一次正确实现而判失败。正常路径已经正确完成时，用对应的故障分支验证修复闭环；只有真实缺陷才能登记为 finding。

以当前版和候选版做成对试验，每个主要场景至少两个独立样例；一旦发现明确质量回退先修复，不继续刷成功次数。接续样例的前驱与后继都使用真实宿主会话；不得把脚本预置 ledger 冒充长任务接续。预先准备的用户决定、工具权限与业务资料在两组完全相同，答案仅在对应澄清节点提供，不能把实验脚本写入的批准当作 agent 自己理解了需求。

长案例采用既有 TaskRef、批准计划、阶段交付记录和所需 checkpoint 表达，不增加多模块调度器或新状态；独立测试覆盖端到端行为、负向/权限/兼容路径及修复回归。不能为使候选通过而降低原项目验收或固定隐藏实现步骤。

无流程 Skill 不作为 man 的合格替代组。仅普通 Solo 或能力定位实验可按需使用该诊断条件，所有组仍遵守相同用户标准和知识可达性。沿用隔离目录、CLI 回执和日志记录方式；历史结果不覆盖，正式失败全部保留，环境探针另记。

先在可用 Codex 宿主完成对照。Claude Code 若可用，再做同类关键样例；不可用则明确“Claude 仅完成生成契约验证”，不宣称真实行为已验证，不自动安装或修改用户全局配置。

观察业务测试、实际 diff、架构与集成结果、工具轨迹、公共 ledger 和最终状态。man 先逐项核对长任务质量与接续要求，再参考成本；Solo 单独记录必要/不必要提问、额外文件、重复检查、耗时与可用 token。必要调研、审核、复验和恢复读回不能被标成无效操作。少量重复是筛查回退，不是普遍保证。

## 6. 更新入口与失败恢复

1. 开发和试验先用隔离项目，保存改前与改后生成内容；不升级当前工作区来消除已安装入口的版本差异。
2. 测试通过后给出候选差异及结果，再按授权范围通过既有 adapter upgrade dry-run 和对应 operation 确认流程发布托管内容。
3. 保留用户自写区、模式发现路径、各平台 client/session 参数；不手工改 managed block，不静默升级历史任务 policy。
4. 单纯精简失败时撤回本次对应模板改动并重新构建，再按相同协议发布；不撤掉此前 nextAction 修复，不清空任务账本。
5. 升级中断时修复原 operation；不删除 journal、不重复创建操作，也不声称存在任意版本的一键回滚。

全局安装、包发布、远端推送和用户其他项目升级，不因本方案文档自动获得执行授权。
